## Read-only root

The original v1.0 plan deferred overlayfs root to v1.1. The script
ships in this release. Workflow:

```bash
# On a quiescent device, as root:
sudo ./scripts/readonly_root.sh enable
sudo reboot

# Verify after boot:
sudo ./scripts/readonly_root.sh status
# overlay marker : enabled
# current root   : overlay
# upper          : /var/lib/signal/overlay/upper
# upper size     : 4.0K

# To install apt updates, temporarily disable:
sudo ./scripts/readonly_root.sh disable
sudo reboot
sudo apt update && sudo apt upgrade
sudo ./scripts/readonly_root.sh enable
sudo reboot
```

State that **must** survive boots (and is deliberately *not* on the
overlay):

* `/var/lib/signal/keys/` — Ed25519 mesh keypair
* `/var/lib/signal/index/` — assistant index
* `/var/lib/signal/models/` — assistant model weights
* `/var/lib/kiwix/` — ZIM library
* `/etc/signal/` — owner token, version pin

State that is **intentionally wiped** on reboot (overlay or no overlay):

* The notes board (tmpfs by design)
* DHCP leases (handed out fresh on every boot)
* Logs (now tmpfs-backed via the fstab block written by the enable step)

## Mesh radio data planes

Both data planes are scaffolds: the daemon units, the Python bridges,
and the setup scripts all ship in this commit, but neither has been
exercised against real hardware. The control plane on
`signal-mesh.service` learns to mount them automatically via lazy
attachment in `mesh.signal_mesh.main._ensure_bridges()`, so once the
hardware is wired up nothing in the user-facing code needs to change.

### LoRa (`signal-reticulum.service`)

Requires:

* RAK4631 (or compatible) USB LoRa hat on `/dev/ttyUSB*`
* `pip install rns` in `/opt/signal/venv/reticulum/` (the operator
  drops a Reticulum config in `/etc/signal/reticulum/`)

### Wi-Fi mesh (`signal-batman.service`)

Requires:

* Second USB Wi-Fi adapter on a channel not used by the client AP
* `/etc/signal/mesh.conf` with at minimum `MESH_IFACE=` set
* `batctl` + `alfred` from apt

`scripts/batman_setup.sh up` is idempotent — re-running over an
already-up mesh is a no-op.

## Mesh-propagated notes (Phase 9.2)

`signal-notes` now calls `signal-mesh` after every successful local
post. The mesh service signs the envelope, hands it to whichever radio
bridges are up, and reports back which ones queued the message. This
is best-effort: a node with no mesh hardware just keeps notes local,
exactly as in v1.0.

## Listen audio bridge (Phase 8.3 scaffold)

`audio_bridge.AudioFanout` is the producer-side primitive: one rtl_fm
stdout, many WebSocket consumers, bounded queues with drop-on-overflow
so a slow client never stalls the dongle. The FastAPI WebSocket
endpoint wires in once we have a Pi 4 + dongle on the bench to tune
buffer sizes against — `audio_bridge.py` keeps the framing stable so
that change is purely additive.

## ADS-B (Phase 8.4)

`adsb.html` + `adsb.js` render `dump1090-mutability`'s `aircraft.json`
directly. nginx aliases `/adsb/` to the decoder's output directory so
the page does not wait on `signal-listen`. With no decoder installed,
the page surfaces a calm "dump1090 isn't running yet" message.

## Acceptance

Per file, exercised by unit tests where they don't need hardware:

* `mesh/signal_mesh/tests/test_bridges.py` — bridges report
  `unavailable` cleanly when sockets / binaries are missing; the Wi-Fi
  bridge parses canned `batctl o -nH` output correctly.
* `listen/signal_listen/tests/test_audio_bridge.py` — bounded queue
  drops on overflow; fanout add/remove is idempotent.
* `notes/signal_notes/tests/test_notes.py` — note posting still works
  when mesh is unreachable (the mesh-client call must return False
  silently, not raise).
