## Signed mesh envelopes

In v1.1 the mesh `POST /notes/publish` path emitted unsigned envelopes
— `messages.make_note(... priv=b"\x00" * 32 ...)` — because the
running `signal-mesh.service` did not have the private bytes loaded in
memory. v1.2 fixes that without weakening the daemon's filesystem
sandbox.

### Two units instead of one

We split key generation off into a new oneshot:

```
[Unit]
Description=SIGNAL mesh Ed25519 keypair provisioning (oneshot)
Before=signal-mesh.service
PartOf=signal-mesh.service

[Service]
Type=oneshot
RemainAfterExit=yes
StateDirectory=signal/keys
ExecStart=… identity.load_or_create() …
```

`signal-mesh.service` is now `Requires=signal-mesh-keygen.service`, so
the daemon never starts without the keys in place. The daemon itself
drops `ReadWritePaths=/var/lib/signal/keys` entirely and instead
imports the bytes via:

```
LoadCredential=ed25519_priv:/var/lib/signal/keys/ed25519.priv
LoadCredential=ed25519_pub:/var/lib/signal/keys/ed25519.pub
```

systemd's credential manager copies both files into a tmpfs-backed
`$CREDENTIALS_DIRECTORY` *as root* before stepping down to the
daemon's dynamic user. `identity.load_from_credentials()` reads from
there in production, falling back to the on-disk path for tests and
for the keygen unit itself.

### Why a oneshot vs. an `ExecStartPre=`

`LoadCredential=` requires its source file to exist at unit-start.
If we kept generation inside `signal-mesh.service` as an
`ExecStartPre=`, the credential manager would have already run before
that hook fires — first boot would always fail.

A separate oneshot that runs `Before=` the daemon lets first-boot "just
work" while still letting the daemon ship without filesystem access to
the secret material.

## QR fingerprint codes

`mesh.signal_mesh.qrcode` is a hand-rolled encoder vendored into the
repo. The offline-first invariant rules out fetching a QR library at
provision time, and the spec slice we need is narrow enough to keep
direct:

- **Versions 1-3** only. Capacity at ECC level M is 14, 26, and 44
  data codewords respectively — the 29-char fingerprint lands cleanly
  in version 3 (29×29 matrix, ~232px at 8 modules per pixel).
- **Byte mode** encoding. Covers the base32 fingerprint with no need
  for the alphanumeric-mode bit packing.
- **ECC level M** (≈15% recovery). Higher than L because a partly-glared
  fingerprint is still the only authentication signal in the trust
  workflow.
- **All 8 masks** evaluated, lowest-penalty mask wins.

The endpoint:

```
GET /api/mesh/identity.svg
→ Content-Type: image/svg+xml
→ Cache-Control: public, max-age=60
```

`peers.html` embeds it as an `<img>` with `loading="lazy"` and an
on-error handler that hides the figure when the upstream is offline.
The image carries `alt="QR code of this node's mesh fingerprint"` so a
screen reader announces it without forcing the user to scan.

### Why we do not encode a URL

We considered encoding `signal://trust/<fp>` or `http://hub.local/...`
inside the QR. We rejected both:

- `signal://` would need a custom mobile handler nobody has installed.
- `http://hub.local/...` only resolves on the *issuing* hub's network,
  which is exactly the opposite of the cross-hub trust workflow this
  feature exists for.

Plain fingerprint text is the simplest and most portable payload — any
QR app on any phone surfaces the same 29 characters, which the user
then pastes into their own `/peers` page.

## Tests

All exercise without hardware:

* `mesh/signal_mesh/tests/test_mesh.py`
  - `test_load_from_credentials_prefers_credentials_dir` — when
    `CREDENTIALS_DIRECTORY` is set, identity reads from there and
    leaves the on-disk path untouched.
  - `test_load_from_credentials_falls_back_to_disk` — no
    `CREDENTIALS_DIRECTORY` → read from `PRIV_PATH`/`PUB_PATH`.
  - `test_load_from_credentials_stub_when_nothing_present` — daemon
    stays up with a deterministic stub bundle.
  - `test_publish_note_signs_with_real_key_when_available` — a real
    Ed25519 keypair round-trips through `messages.make_note()` and
    verifies under the corresponding public key.
* `mesh/signal_mesh/tests/test_qrcode.py`
  - Version auto-pick (short input → v1, fingerprint → v3).
  - Finder, alignment, timing, dark-module structural invariants.
  - Oversize input raises `ValueError`.
  - SVG output is well-formed, declares the XML namespace, has no
    `<script>` tags, and scales with `module_px`.
  - Encoding is deterministic.

## Acceptance

Per the project's per-unit "ship when these pass" rule:

- `signal-mesh-keygen.service` is enabled on a fresh image install.
- `systemctl status signal-mesh.service` lists `signal-mesh-keygen.service`
  under `Requires`.
- `journalctl -u signal-mesh.service | grep "CREDENTIALS_DIRECTORY"`
  shows the credential dir was populated.
- `curl http://127.0.0.1:8500/identity.svg` returns SVG starting with
  `<svg`, content-type `image/svg+xml`.
- `http://hub.local/peers.html` renders the QR figure beneath the
  fingerprint.
- `POST /api/mesh/notes/publish` on the loopback (signal-notes calls
  this) produces an envelope whose `sig` verifies against the public
  key surfaced by `/api/mesh/identity`.

## v1.2.1 follow-up — dump1090 install gate

The "dump1090-mutability install integration" backlog item that v1.1
flagged is closed in v1.2.1. Detail:

- **`scripts/detect_rtlsdr.sh`** — exits 0 when `lsusb` shows a known
  RTL2832U USB device. Vendor/product IDs sourced from librtlsdr's
  `known_devices[]` table.
- **`config/dump1090/dump1090-mutability.default`** — `/etc/default/`
  override that flips `START_DUMP1090="yes"`, points the JSON output
  at `/run/dump1090-mutability/` (which nginx's `/adsb/` alias already
  serves), and disables both the BaseStation TCP port and dump1090's
  own embedded HTTP listener (`NET="no"`, `HTTP="no"`). Two HTTP
  listeners on the same JSON would only confuse a reader.
- **`install.sh` phase 8.4 sub-flow** — `phase8_adsb()` runs the
  detector. If a dongle is present, it installs the default file and
  enables + starts the unit. If not, it leaves the unit disabled and
  prints an operator-friendly instruction for opting in later.
- **`api/signal_status/system.py:_probe_adsb`** — file-based probe:
  `aircraft.json` mtime ≤ 30s and parseable JSON → `"ready"` + live
  aircraft count. The status page renders that count inline
  (`"ready · 7 aircraft"`).
- **`/api/status`** surfaces a new `adsb` + `adsb_aircraft` pair on
  the `services` block; status.html / status.js render an "ADS-B" row
  in the per-service grid.

Single-dongle mutual exclusion: if both `signal-listen-same` (NOAA
SAME monitoring on 162.4 MHz) and `dump1090-mutability` (ADS-B on
1090 MHz) are enabled with one dongle attached, one of the two will
fail to claim the device and surface as `"not-running"` on the status
page. Operators with a single dongle should disable the mode they're
not using; operators with two dongles can pin each unit to a specific
`DEVICE=` index in the respective config.
